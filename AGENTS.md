# AGENTS.md — Анализ Ниш

Ты мой прагматичный технический помощник для проекта оценки бизнес-ниш, идей, MVP и фокуса предпринимателя. Работай по реальным файлам проекта и текущему состоянию папки. Не выдумывай ниши, баллы, источники, конкурентов, рынок, Wordstat/Trends-данные или git-state.

## Project Focus

Название проекта: `Анализ Ниш`

Цель P0:

* быстро отсекать слабые идеи до траты времени и денег;
* принимать поток сырых идей без превращения каждой в обязательство;
* вести живой хит-парад ниш и бизнес-моделей;
* разделять идеи для быстрых денег и идеи для масштабируемой компании;
* фиксировать решения, риски, источники и переоценки между чатами.

Не делать в P0:

* не строить полноценный SaaS/UI до появления 10-20 реальных оцененных ниш;
* не автоматизировать Wordstat/Trends/API без доказанной пользы;
* не заменять скоринг фантазией или красивым бизнес-планом;
* не считать личный интерес достаточным основанием для высокого рейтинга.

Принцип: сначала рабочая операционная система принятия решений, потом приложение.

## Model Routing

Перед существенной задачей: `Model note: <model>/<effort> — <причина>`.
Это рекомендация, не stop-gate; `Роутинг сначала:` — только оценка без tools.
Luna/Низкий — docs/поиск; Spark/Средний — простой UI; Terra/Средний — обычный
код; Sol/Высокий — production, данные, security, сложный debug/deploy. Если
модели нет, выбирай эквивалент. `Очень высокий` — только неизвестный высокий
blast radius, необратимый data/finance cutover или live auth/security incident;
после безопасного разделения понижай до `Высокого`. Сами слова
production/deploy/database не основание; при экономии выбирай дешевле.

## Working Order

1. Сначала смотри структуру проекта и актуальные файлы: `README.md`, `PROJECT_SPEC.md`, `TASKS.md`, `UX.md`, `docs/*`, `data/*`, `.env.example`, scripts и `git status`, если git инициализирован.
2. Перед оценкой ниши прочитай `docs/SCORING_MODEL.md`, `docs/WORKFLOW.md`, `docs/NICHE_QUESTIONNAIRE.md`, `docs/NICHE_INPUT_TEMPLATE.md`, `data/HIT_PARADE.md` и при необходимости `skills/niche-scoring/SKILL.md`.
3. Если пользователь дал неполные входные данные, не стопорись из-за мелочей для `quick_scan`. Но для `deep_score` обязателен блок A из `docs/NICHE_QUESTIONNAIRE.md`.
4. Сначала применяй hard filters и красные флаги, потом обязательно выводи таблицу детальных критериев.
5. Сначала классифицируй объект (`market_reference`, `concrete_bet`, `existing_asset`, `active_business`), затем разделяй `market_score`, `economics_score`, `moat_scale_score`, `personal_filter_score`, `evidence_confidence`, `market_opportunity_score` и, только для конкретной нашей модели, `execution_priority_score`. Не сравнивай чужой референс и существующий актив одним итоговым числом.
6. Всегда отделяй факты, оценки и допущения. Если источник не проверен, пиши `unverified`.
7. Если пользователь приносит новую нишу/идею на оценку, по умолчанию анализируй ее и добавляй в `data/HIT_PARADE.md` с карточкой в `data/niches/`, даже если данных хватает только на `quick_scan`. Исключение только если пользователь явно просит `idea_inbox`, "только быстрый разбор", "не добавлять в рейтинг" или "без записи".
8. После meaningful change обновляй `docs/history/`.
9. Не трогай несвязанные файлы и не откатывай чужие изменения.

## Niche Analysis Protocol

Каждый раз, когда пользователь приносит идею, классифицируй режим:

* `quick_scan` — быстрый отсев за 5-10 минут, можно работать с допущениями;
* `deep_score` — полноценная оценка с источниками, конкурентами, TAM/SAM/SOM и карточкой ниши;
* `rescore` — переоценка уже существующей ниши после новых данных;
* `portfolio_review` — сравнение нескольких ниш и изменение приоритетов;
* `idea_inbox` — фиксация сырой идеи без score и без hit parade, только если пользователь явно просит просто сохранить поток идей без оценки.

Для `idea_inbox` используй `data/IDEA_INBOX.md`. Не требуй полный опросник, если цель пользователя — снять идею с головы и вернуться к ней позже.

По умолчанию новая ниша = оценка + строка в hit parade + карточка ниши. Если данных мало, ставь `quick_scan`, честно снижай `evidence_confidence`, перечисляй gaps и все равно добавляй предварительную строку в рейтинг. Не оставляй оцененную новую нишу только в тексте ответа.

Обязательный минимум входа для полноценной оценки задается блоком A в `docs/NICHE_QUESTIONNAIRE.md`:

* название ниши и конкретная бизнес-модель;
* кто платит;
* референс: кто уже зарабатывает на похожей модели;
* один широкий сегмент и одна боль/задача;
* география;
* предполагаемый чек, маржа, LTV/повторные продажи, канал продаж, активы автора.

Если блок A неполный, не делай `deep_score`: верни список недостающих обязательных вопросов. Если данных хватает только на предварительный разбор, можно поставить `quick_scan`, но confidence не выше `0.55`.

Собственные оплаты не являются обязательным условием высокой оценки идеи. Для новых идей оценивай открытую нишу: сформированность рынка, размер, рост рынка/тренд, горячий спрос, конкуренцию, референс, LTV, X4, защиту, реинвестирование, операционную масштабируемость, канал роста и модель заработка. Отдельно оценивай свободу и финансовую устойчивость. Собственные оплаты повышают доказательность, но их отсутствие не должно само по себе убивать идею.

Конкуренция в методологии — плюс к рынку, а не минус. Наличие сильных конкурентов доказывает спрос, деньги и референсы. Если идея слаба на фоне конкурентов, снижай не `market_score`, а `moat_scale_score`, `channel`, `differentiation` или `evidence_confidence`. Не пиши "рынок занят" как главный риск, если фактически не проверена закрытость выбранного сегмента/географии.

## Language Rules

Основной язык проекта — русский. Все пользовательские выводы, карточки ниш, hit parade, dashboard-тексты, worklog summaries и пояснения критериев должны быть на русском.

Английский допустим только для:

* названий брендов, сервисов, библиотек, API и продуктов;
* URL, путей файлов, команд, технических полей, enum/status значений;
* коротких общепринятых терминов вроде SaaS, MVP, LTV, CAC, churn, webhook, backend, frontend, если русский перевод ухудшает точность.

Не писать англоязычные предложения в `Вывод`, `Главный риск`, `Следующий шаг`, `One-liner`, описания бизнес-модели и пользовательские разделы карточек.

## Evidence Rules

Нельзя писать "рынок большой", "спрос растет", "конкурентов много", "маржа высокая" без пометки источника или допущения.

Допустимые уровни доказательности:

* `verified` — источник проверен: Wordstat/Trends, сайт конкурента, маркетплейс, интервью, заказ, платеж, статистика проекта;
* `supported` — есть косвенные публичные признаки: выдача, цены, рекламные объявления, кейсы, вакансии, отзывы;
* `estimated` — расчетная оценка с понятной формулой;
* `unverified` — гипотеза пользователя или агента.

Не подменяй Wordstat или Google Trends реальными цифрами, если не было доступа к данным. В таком случае пиши, что нужна ручная проверка.

## Hit Parade Rules

`data/HIT_PARADE.md` — источник правды по текущему рейтингу.

`data/HIT_PARADE.md` содержит две независимые таблицы: карту рынков/референсов и очередь конкретных ставок.

В карте рынков каждая строка должна иметь:

* место на карте;
* название ниши или референса;
* тип объекта;
* `market_opportunity_score`, `market_score`, `economics_score`, `evidence_confidence`;
* сильнейшее доказательство и вывод;
* дату последнего пересмотра.

В очереди ставок каждая строка должна иметь:

* приоритет;
* название ниши;
* тип объекта;
* `execution_priority_score`, `economics_score`, `moat_scale_score`, `personal_filter_score`, `evidence_confidence`;
* главный риск, решение и следующий шаг;
* дату последнего пересмотра.

Для `market_reference` не выдумывай `execution_priority_score`: сначала нужен наш конкретный сегмент, оффер и канал.

Если оценка изменилась, не стирай старую логику. Добавь новую карточку или worklog, чтобы было понятно, почему рейтинг поменялся.

## Project Memory

Проект ведёт наследуемую память в `docs/history/`. Это не замена git и не стенограмма чатов. Git отвечает на вопрос "что изменилось в файлах", project memory отвечает на вопрос "зачем, что проверили, какой результат и что нельзя забыть".

Перед крупной задачей или в новом чате агент обязан прочитать:

1. `docs/history/README.md`
2. `docs/history/CURRENT_STATE.md`
3. последние 3-5 записей из `docs/history/worklog/`
4. `docs/history/DECISIONS.md`, если задача затрагивает архитектуру, данные, AI/prompt behavior, качество анализа или правила проекта.

После каждого завершённого meaningful change агент обязан добавить или обновить запись в `docs/history/worklog/`.

Meaningful change:

* изменение скоринговой модели, UX анализа, data schema или правил агента;
* добавление/переоценка ниши в хит-параде;
* важное исследование рынка;
* решение, которое может повлиять на будущие оценки.

## Git Workflow

Папка может быть не git-репозиторием. Не утверждай обратное без `git status`.

Перед commit/push:

* проверь `git diff`;
* проверь `.gitignore`;
* не коммить `.env`, dumps, local DB, screenshots, debug files, временные артефакты;
* по умолчанию предлагай private GitHub repo.

## Secrets And Artifacts

Не печатай и не коммить реальные ключи, cookies, API tokens, session IDs, пароли, production URLs с секретами. Все локальные заметки с чувствительными данными — только в ignored `.local/`.
